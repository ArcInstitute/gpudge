# Third-party licenses

License audit of the packages `gpudge` depends on. **`gpudge` itself is
licensed `MIT`** (see `LICENSE` and `pyproject.toml`).

> **Audited 2026-08-02** against a **recorded point-in-time clean environment
> resolved from the `v0.7.0` tree** (CPython 3.12.11, uv 0.7.12, the `cu126`
> PyTorch build, `dev` + `fast` + `streaming-gpu` extras; 93 distributions). The
> recipe below is the method — use it for the next audit; it is not guaranteed to
> reproduce these exact versions, and is not meant to.
>
> **These versions are a point-in-time resolve, not committed project state.**
> gpudge declares floors (`anndata>=0.12`, `torch>=2.5`, …) against a mutable
> index, so only `shardad` — tag-pinned via `[tool.uv.sources]` — is fixed by the
> repository; everything else is what the resolver returned on 2026-08-02. The
> `uv.lock` generated by that run — `$AUDIT/tree/uv.lock` in the recipe below —
> has SHA-256
> `dd5a4aa115eb0a9ddaca8a1b83024745452cd13328e2258959f8f04fa15e01d8`. Re-audit
> after dependency bumps.
>
> **Not** the developer `.venv`: that environment installs `shardad` from a local
> working checkout (`direct_url.json` → `file:///…/shardad`, version
> `0.7.2.dev24+…`), which is not evidence for any released version, and it carries
> unrelated editable installs that are outside gpudge's dependency closure.
>
> **Package-level** licenses were read from installed distribution metadata, not
> assumed. Where a package carries no **structured license identifier** — no
> `License-Expression`, no legacy `License` value, no `License ::` classifier —
> the `LICENSE` file shipped in the distribution (referenced by `License-File:`)
> is cited instead and called out as such. Where the *only* identifier is the
> coarse legacy `BSD License` classifier (SciPy, numba), the precise SPDX
> identifier is resolved from the shipped license text and marked "from
> `LICENSE`" — metadata alone cannot distinguish 2-clause from 3-clause. Where a
> package has **neither** — no identifier *nor* any license file in any published
> artifact (`pyfastpfor`) — the grant is taken from the license headers carried in
> that release's own source, cited by file, and flagged as an artifact-level gap
> rather than recorded as a clean license. Claims about *bundled components* whose
> license information the wheel does not itself carry (notably hdf5plugin's HDF5
> filters — the wheel ships the eleven filter `.so` binaries, but nothing stating
> their terms) are attributed to upstream and flagged as such.
>
> Supersedes the 2026-06-09 audit, which predated the MIT relicense (#60) and
> therefore described gpudge as BSD-3-Clause throughout.
>
> Supersedes the 2026-07-25 audit, which was taken against the developer `.venv`
> and therefore recorded a `shardad` version predating the `[cell]` extra entirely,
> and omitted `pyfastpfor` and `pybind11` (gpudge_arc#120).

## How to regenerate

First build the environment. Resolve it from a clean checkout of the tagged tree,
never from a developer `.venv` — this is the step whose absence made the previous
audit ambiguous about which environment it described:

```bash
set -euo pipefail   # without errexit a failed mkdir/tar/cd falls through to
                    # `uv sync` in whatever directory you started in

# Put $AUDIT on a large scratch filesystem, never /home: the resolved
# environment is ~8 GB. Substitute your own site's path -- and check that you
# can create a directory there: a shared scratch root is often root-owned 0755,
# in which case $SCRATCH/$USER is NOT creatable and a per-group path is.
SCRATCH_ROOT=/path/to/scratch
AUDIT=$SCRATCH_ROOT/gpudge-license-audit-$(date +%Y%m%d-%H%M%S)
# A fresh, unique directory: `mkdir -p` over a populated path silently overlays
# it, which is exactly the contamination this recipe exists to avoid.
mkdir "$AUDIT" "$AUDIT/tree"
# `-C /path/to/gpudge` is deliberate, not redundant: nothing above this line
# puts you in the gpudge checkout, so a bare `git archive` would depend on an
# unstated cwd. `tar -xf -` names stdin explicitly, which BSD/macOS tar wants.
git -C /path/to/gpudge archive v0.7.0 | tar -xf - -C "$AUDIT/tree"
cd "$AUDIT/tree"
uv sync --python 3.12 --extra dev --extra fast --extra streaming-gpu
```

`[tool.uv.sources]` pins shardad to its `v0.7.1` tag, so that sync resolves
`shardad==0.7.1` from
`git+ssh://git@github.com/ArcInstitute/shardad.git@fbba761` — the version this
audit describes, and the one version here the repository actually fixes. Confirm
it before reading anything else:

```bash
.venv/bin/python -c "import importlib.metadata as M; print(M.version('shardad'))"
# 0.7.1
```

Then dump the closure:

```bash
.venv/bin/python - <<'PY'   # the $AUDIT/tree/.venv from above
import importlib.metadata as M
for d in sorted(M.distributions(), key=lambda d: (d.metadata.get("Name") or "").lower()):
    md = d.metadata
    name = md.get("Name")
    if not name:
        continue
    lic = (md.get("License-Expression")
           or "; ".join(dict.fromkeys(
               v.split("::")[-1].strip() for k, v in md.items()
               if k == "Classifier" and v.startswith("License ::")))
           or (md.get("License") or "").strip().splitlines()[0:1] or ["(none declared)"])
    print(f"{name}\t{d.version}\t{lic if isinstance(lic, str) else lic[0]}")
PY
```

Four caveats when reading that output:

- It reads only the **identifier fields**. Several packages below leave those
  empty yet ship a real `LICENSE` file; check `<dist-info>/licenses/` before
  concluding anything is unlicensed.
- It prefers a `License ::` classifier over the legacy `License` value, so for
  SciPy it prints just `BSD License` and **never reaches** that package's
  ~47 kB `License` value — which is where the bundled binary components and
  their SPDX identifiers are declared. Inspect that field separately; see the
  SciPy subsection below.
- It reports **whatever is installed**. In the clean environment above that *is*
  gpudge's dependency closure for those extras (93 distributions, `gpudge` itself
  included). Run it against a developer `.venv` and it is not: that environment
  also carries unrelated editable installs, which is one more reason the recipe
  above starts from `git archive`.
- A `License ::` classifier can be **present and still name nothing**. `umap-learn`
  declares exactly `License :: OSI Approved`; because the snippet keeps only the
  segment after the final `::`, that prints as a bare `OSI Approved`. Treat any
  output that does not name a license family as "not yet audited".

### SciPy's bundled shared libraries

The manylinux wheel vendors compiler-runtime and BLAS libraries into
`scipy.libs/`. These are **declared by the wheel**, in the legacy `License`
metadata value, each with an SPDX identifier and the file it covers:

| Bundled component | Files | License |
|---|---|---|
| OpenBLAS | `libscipy_openblas*.so` | BSD-3-Clause |
| LAPACK | `libscipy_openblas*.so` | BSD-3-Clause-Open-MPI |
| GCC runtime library (`libgfortran`) | `libgfortran*.so` | GPL-3.0-or-later WITH GCC-exception-3.1 |
| libquadmath | `libquadmath*.so` | LGPL-2.1-or-later |

(The wheel's CycloneDX SBOM, `<dist-info>/sboms/auditwheel.cdx.json`, lists
`libgfortran` and `libquadmath` as components but carries **no** license
entries for them, and does not inventory `libscipy_openblas` at all. The legacy
`License` value is the authoritative source here, not the SBOM.)

This matters only for **redistribution** of an assembled environment, not for
using gpudge. Two notes on the copyleft entries:

- **GCC-exception-3.1** permits Target Code that combines the runtime library
  with Independent Modules to be conveyed under terms of your choice, provided
  the Target Code came from an Eligible Compilation Process. That is what stops
  GPL copyleft reaching the qualifying combined work — it does **not** make
  `libgfortran` itself permissive; that library remains GPL-covered with its own
  redistribution obligations.
- **`libquadmath` is LGPL-2.1-or-later** with no such exception, so it carries
  the usual LGPL notice, source-availability and relinking obligations on
  redistribution.

## Transitive dependencies requiring attention

### The `[cell]` extra: `pyfastpfor` and `pybind11`

New since the 2026-07-25 audit. Both arrive through the `streaming` extras. Only the
first edge of the chain is visible in gpudge's own `pyproject.toml` (lines 51, 56);
the rest is not, which is why neither package appeared in earlier audits:

```
gpudge[streaming]      ->  shardad[cell]>=0.7.1       (pyproject.toml:51)
gpudge[streaming-gpu]  ->  shardad[cell,gpu]>=0.7.1   (pyproject.toml:56)
shardad[cell]          ->  pyfastpfor>=1.4            (shardad's `extra == "cell"`)
pyfastpfor             ->  pybind11>=2.4              (unconditional Requires-Dist)
```

`pyfastpfor` is not optional at install time: shardad requires it with no condition
beyond `extra == "cell"`, and both of gpudge's streaming extras select that extra,
so every `streaming` install pulls it in. At runtime shardad imports it
lazily, and only for `codec='pfordelta'` cell archives — `codec='zstd'` opens
without it — but `pfordelta` is what every production `.csad` uses.

| Package | Version | License | Notes |
|---|---|---|---|
| pyfastpfor | 1.4.0 | Apache-2.0 **per the release's own source headers** — no license file in any published artifact | see flag 6 |
| pybind11 | 3.0.4 | BSD-3-Clause | permissive; declares a real `License-Expression` **and** ships `LICENSE` (© 2016 Wenzel Jakob). No gap |

**`pyfastpfor` ships no license file in any artifact.** Being precise about *which*
artifact matters here:

- **PyPI publishes only an sdist** for 1.4.0 — `pyfastpfor-1.4.0.tar.gz`, uploaded
  2023-10-14, with an empty `license` field and an empty `classifiers` array. There
  is **no published wheel**; the `.dist-info` seen in an installed environment
  belongs to a wheel the resolver **built locally** from that sdist.
- **The sdist contains no license file.** All 75 entries scanned: `MANIFEST.in`,
  `PKG-INFO`, `fastpfor/`, `pyfastpfor.cc`, `pyfastpfor.egg-info`,
  `requirements.txt`, `setup.cfg`, `setup.py` — nothing matching
  `licen|notice|copying`.
- **The locally built wheel loses even the in-source notices.** Seven files:

  ```
  pyfastpfor-1.4.0.dist-info/{INSTALLER,METADATA,RECORD,REQUESTED,WHEEL,top_level.txt}
  pyfastpfor.cpython-312-x86_64-linux-gnu.so          (17 MB)
  ```

  No `License-Expression`, no legacy `License`, no `License ::` classifier, no
  `License-File`, and no `LICENSE`/`COPYING`/`NOTICE`. `strings` over the `.so`
  matches no occurrence of `apache`, `copyright`, or `licen[sc]e` (a pattern
  deliberately spanning both spellings) either — the
  compiled artifact carries the grant nowhere at all.

**The grant itself is not in doubt, and the citation is the release's own source** —
not GitHub's current license detector, whose repository-level `LICENSE` is not part
of the 1.4.0 sdist:

- `pyfastpfor.cc`, header comment: *"This code is released under the Apache License
  Version 2.0 http://www.apache.org/licenses/."*
- **51 of the 58** files in the bundled `fastpfor/` tree carry an `Apache License`
  notice. Upstream `lemire/FastPFor` states *"This code is licensed under Apache
  License, Version 2.0 (ASL2.0)"*.

So the terms are Apache-2.0 and permissive. What is missing is artifact-level: the
license copy that **Apache-2.0 §4(a)** obliges a redistributor to give recipients.
§4(d)'s attribution-`NOTICE` duty is **conditional on the original work carrying a
`NOTICE` file**, and neither upstream repository has one — `searchivarius/PyFastPFor`
ships `LICENSE` + `README.md`, `lemire/FastPFor` ships `LICENSE` + `AUTHORS`. So
§4(a) alone is unmet.

Installation as a Torch runtime dependency does not by itself establish that
gpudge exercises every library listed.

### MPL-2.0 (weak, file-level copyleft)

- `certifi` (MPL-2.0)
- `tqdm` (MPL-2.0 AND MIT)
- `fast-array-utils`, `legacy-api-wrap`, `session-info2` (via the `scanpy` dev extra)

**Mere internal use does not trigger MPL distribution or source-availability
obligations.** On **distribution in executable form**, MPL-2.0 §3.2 requires
that the Source Code Form of the covered files be made available under the MPL,
together with the required notices — this applies whether or not you modified
them. "File-level" copyleft bounds *which files* the obligation reaches (not
unrelated files in the Larger Work); it does not mean the obligation attaches
only to files you changed.

### Everything else

The remaining transitive packages in gpudge's dependency closure are permissive
— MIT / BSD / Apache-2.0 / PSF. (No count is given deliberately: it drifts with
every dependency bump.)

## Compliance flags

1. **Proprietary NVIDIA CUDA components are present.** Most of the CUDA runtime
   set is proprietary (the Apache/MIT exceptions are marked in the table above),
   and `streaming-gpu` adds `nvidia-nvcomp-cu12`. This does not change gpudge's
   own MIT licensing, but use *and* redistribution of those components remain
   governed by NVIDIA's terms — which is what blocks redistributing the
   assembled binary environment under open terms.

2. **Three packages ship a license but declare no identifier.** `shardad`
   (MIT), `hdf5plugin` (MIT, wrapper only — see flag 3), and `google-crc32c`
   (Apache-2.0, a direct requirement of `zarr`; `numcodecs` offers it only under
   an optional extra that is not active here) each have a `License-File` and a
   real grant, but no expression, legacy value, or classifier. No *grant* is
   missing; this is an SBOM/tooling defect. Scanners keyed on the identifier
   fields cannot resolve these from those fields, whereas scanners that read
   `License-File` can. Worth adding a license expression to shardad's
   `pyproject.toml` before any public / PyPI release that references it.

   *Resolved since the previous audit:* shardad had no `LICENSE` file at all at
   0.2.0, which that audit correctly flagged as all-rights-reserved by default.
   It has since been licensed MIT.

   A neighbouring case where the identifier fields *are* populated but say nothing:
   `umap-learn` (transitive, via the `scanpy` dev extra) declares the bare
   classifier `License :: OSI Approved` — naming no license family — over a legacy
   `License` value of just `BSD`. Its shipped `LICENSE.txt` is BSD 3-Clause
   (© 2017 Leland McInnes). Same remedy, same non-issue for rights.

3. **`hdf5plugin`'s bundled filters are not covered by its MIT grant.** The
   shipped `LICENSE` grants MIT for the hdf5plugin code itself; the bundled HDF5
   filters have their own terms, and the wheel includes neither their notices
   nor upstream's `doc/information.rst` enumerating them. Redistributing the
   assembled artifact needs a separate review of those filter licenses — this is
   not merely a metadata gap.

4. **`cuda-toolkit` has no grant to point at.** No identifier, no `License-File`,
   no license text in the wheel. It is an empty NVIDIA metapackage, so exposure
   is **low — not nil**: its redistribution status is genuinely unknown rather
   than resolved, and the installed wheel does not establish which NVIDIA terms
   govern.

5. **SciPy's wheel bundles `LGPL-2.1-or-later` (`libquadmath`) and
   `GPL-3.0-or-later WITH GCC-exception-3.1` (`libgfortran`).** Use is
   unaffected; redistribution of the assembled environment is not purely
   permissive.

6. **`pyfastpfor` ships no license copy in any published artifact, and it is an
   unconditional member of the `streaming` closure.** shardad requires it with no
   condition beyond `extra == "cell"` (`Requires-Dist: pyfastpfor>=1.4; extra ==
   "cell"`), and both streaming extras select that extra, so installing either one
   always installs it — which is what puts it in scope here. (At *runtime* it is imported
   lazily and only for `codec='pfordelta'` cell archives; shardad's cell layout
   also supports `codec='zstd'`, which opens without it. `pfordelta` is what every
   production `.csad` uses.) PyPI carries only an sdist for 1.4.0,
   and that sdist has no `LICENSE`/`NOTICE`/`COPYING` among its 75 entries; the
   wheel a resolver builds from it is seven files with no license metadata and a
   `.so` that embeds no license text. The grant is nevertheless clear from the
   release's **own source** — `pyfastpfor.cc`'s header states Apache-2.0, as do 51
   of the 58 bundled `fastpfor/` files — so the **terms are permissive and the
   license is established**; what is absent is the artifact-level copy.
   **Apache-2.0 §4(a)** requires a redistributor to give recipients a copy of the
   License, so **redistributing an assembled environment containing this package
   means adding that copy yourself, from an authoritative source** — §4(a) governs
   conveying the text, not where you obtain it, and the package supplies it
   nowhere. (§4(d)'s `NOTICE` duty is conditional on the original work having a
   `NOTICE` file; neither `searchivarius/PyFastPFor` nor `lemire/FastPFor` has one,
   so it does not apply.) This is a **missing-license-copy** problem: strictly worse
   than flag 2's packages, which ship a real grant and merely fail to declare an
   identifier, and distinct from flag 3's hdf5plugin case, which is a
   missing-*notice* problem for components under terms the wheel never states.
   Worth reporting upstream.

**Net:** everything gpudge itself authors is MIT, and every direct dependency's
*project-level* license is permissive. `pyfastpfor`, although transitive rather than
direct, is likewise Apache-2.0 at the project level even though its published
artifacts carry no license copy (flag 6). **Using** gpudge triggers no copyleft or
disclosure obligation.

**Redistributing an assembled environment is a separate question and is not
purely permissive.** It carries NVIDIA's proprietary terms; MPL-2.0 §3.2
source-availability for five packages; SciPy's bundled `LGPL-2.1-or-later` and
`GPL-3.0-or-later WITH GCC-exception-3.1` runtime libraries (so the installed SciPy *artifact* is
not purely permissive even though the SciPy *project* is BSD-3); hdf5plugin's
bundled-filter terms, whose notices the wheel does not ship; `pyfastpfor`'s
Apache-2.0 license copy, which §4(a) obliges a redistributor to convey and which
must be added from an authoritative source because no published artifact contains
it (flag 6); and `cuda-toolkit`, whose governing terms are simply unknown.
Separately, the identifier gaps in
flag 2 — and `umap-learn`'s content-free classifier — affect SBOM generation
rather than rights; flag 6 is **not** in that category, because a missing license
copy is a redistribution obligation, not a tooling defect.
